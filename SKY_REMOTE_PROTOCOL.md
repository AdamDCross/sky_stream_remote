## 1. Overview

The Sky Remote protocol allows an IP-based remote control client to discover, pair with, authenticate to, and control a Sky set-top box (STB) on the local network. The protocol stack is:

```
┌──────────────────────────────┐
│   Key Commands (JSON)        │
├──────────────────────────────┤
│   Pair / Bind (JSON)         │
├──────────────────────────────┤
│   WebSocket (/iptarget)      │
├──────────────────────────────┤
│   TLS 1.3 (mTLS required)   │
├──────────────────────────────┤
│   TCP port 8091              │
└──────────────────────────────┘
```

**Session lifecycle:**

```
Discovery → TLS+mTLS Connect → WebSocket Upgrade → Pair → Auth Token → Bind → Commands
```

## 2. Device Discovery

Sky STBs advertise themselves on the local network via **mDNS** (Zeroconf/Bonjour).

| Field | Value |
|-------|-------|
| Service type | `_rics._tcp.local.` |
| Port | `8091` |
| Properties | `wol_mac`, `wowl_mac` (MAC address for Wake-on-LAN) |

### Wake-on-LAN

If the device is in standby, a WoL magic packet can be sent to its MAC address (from the mDNS `wol_mac` property) on UDP port 9 to wake it before connecting.

The magic packet consists of 6 bytes of `0xFF` followed by the 6-byte MAC address repeated 16 times (102 bytes total), broadcast to `255.255.255.255:9`.

## 3. TLS Connection

The STB listens on **TCP port 8091** and requires **TLS 1.3** with **mutual TLS (mTLS)** — the client MUST present a valid client certificate or the connection is rejected with `TLSV13_ALERT_CERTIFICATE_REQUIRED`.

### SSL Context Configuration

| Parameter | Value |
|-----------|-------|
| Protocol | TLS 1.3 (minimum TLS 1.2) |
| Cipher | `TLS_AES_256_GCM_SHA384` (negotiated) |
| Server certificate verification | **Disabled** (`CERT_NONE`) |
| Check hostname | **Disabled** |
| SNI (Server Name Indication) | `sky.xcal.tv` |
| ALPN | `http/1.1` |
| Client certificate | EC P-256 leaf + chain (see [§11](#11-embedded-credentials)) |
| Client private key | EC P-256 private key |

### Client Certificate Details

| Field | Value |
|-------|-------|
| Subject CN | `sky.xcal.tv` |
| Subject UID | `1DJ4xS3Rv9D3VJNtJq7QDqUkzxsXkZr3ry` |
| Key type | EC P-256 (ECDSA-SHA256) |
| Chain | 3 certificates (leaf → intermediate → root) |
| Leaf SHA-256 fingerprint | `a16031cd083792e156b761a5682c0069e37eeb119d7ccf32597f2f53e1fd859e` |

> **Important:** The SHA-256 fingerprint of the leaf certificate's DER encoding is a critical input to the authentication token derivation (see [§6](#6-authentication-token-derivation)).

## 4. WebSocket Handshake

After TLS is established, the client upgrades to a WebSocket connection.

| Parameter | Value |
|-----------|-------|
| URI path | `/iptarget` |
| Full URI | `wss://<device-ip>:8091/iptarget` |
| Origin | `https://<device-ip>:8091/` |
| User-Agent | `Dart/3.9 (dart:io)` |
| Cache-Control | `no-cache` |
| Accept-Encoding | `gzip` |
| Compression | **None** (permessage-deflate disabled) |

All subsequent messages are JSON objects exchanged as WebSocket text frames.

## 5. Pairing

Pairing establishes a session between the client and the STB. The STB automatically accepts pair requests — no user interaction is required on the TV.

### Pair Request (Client → STB)

```json
{
    "command_name": "Pair Request",
    "tid": "<transaction-uuid>",
    "name": "Soft Remote",
    "manufacturer": "Comcast",
    "model": "IPRemote",
    "controllernonce": "<uuid>"
}
```

| Field | Description |
|-------|-------------|
| `tid` | Transaction ID — a random UUID (v4). Used to correlate request/response. |
| `name` | Display name for the remote (arbitrary string). |
| `manufacturer` | Must be `"Comcast"`. |
| `model` | Must be `"IPRemote"`. |
| `controllernonce` | A random UUID (v4 or v7) generated by the client. **This is a critical input to the auth token** — both the client and device must agree on this value. |

### Pair Response (STB → Client)

```json
{
    "command_name": "Pair Request",
    "name": "Living Room",
    "pairingcode": "                 8 0",
    "status": true,
    "stbnonce": "6VN~E-1}]Q",
    "tid": "<echoed-tid>"
}
```

| Field | Description |
|-------|-------------|
| `name` | The STB's friendly name (e.g., "Living Room"). |
| `pairingcode` | A 20-character string of space-separated digits, right-justified. This is an auth token input. |
| `status` | `true` if pairing accepted. |
| `stbnonce` | A random string generated by the STB. This is an auth token input. |
| `tid` | Echoed back from the request. |

> **Note:** The `pairingcode` is NOT displayed on the TV — it is sent automatically in the response. It is always 20 characters long, containing digits separated by spaces, right-justified (e.g., `"                 8 0"`).

## 6. Authentication Token Derivation

The auth token proves the client's identity to the STB. It is derived from four inputs that both sides know:

| Input | Source | Example |
|-------|--------|---------|
| `cert_fingerprint` | SHA-256 of client certificate DER, as 64 hex chars | `a16031cd...859e` |
| `pairingcode` | From Pair Response | `"                 8 0"` |
| `controllernonce` | UUID sent in Pair Request | `"019ce95f-f60a-7e31-..."` |
| `stbnonce` | From Pair Response | `"6VN~E-1}]Q"` |

### Algorithm (Two-Stage SHA-256)

```
┌─────────────────────────────────────────────────────────────────┐
│  STAGE 1: Inner Hash                                            │
│                                                                 │
│  input  = hex_decode(cert_fingerprint)  ← 32 bytes             │
│         + pairingcode.encode("utf-8")   ← 20 bytes             │
│         + controllernonce.encode("utf-8") ← 36 bytes (UUID)    │
│                                         ─────────              │
│                                          88 bytes total         │
│                                                                 │
│  inner  = SHA-256(input)                ← 32 bytes              │
├─────────────────────────────────────────────────────────────────┤
│  STAGE 2: Final Token                                           │
│                                                                 │
│  input  = stbnonce.encode("utf-8")      ← varies (~10 bytes)   │
│         + inner                         ← 32 bytes             │
│         + "biT43y".encode("utf-8")      ← 6 bytes (salt)       │
│                                                                 │
│  token  = Base64( SHA-256(input) )      ← 44-char string       │
└─────────────────────────────────────────────────────────────────┘
```

### Key Details

- **`cert_fingerprint`**: The SHA-256 hash of the leaf client certificate in DER format, represented as a lowercase 64-character hex string. The STB knows this value because it receives the certificate during the TLS handshake.
- **`"biT43y"`**: A hardcoded salt found in the `libapp.so` binary. It is appended to the second-stage input before hashing.
- The final token is a standard Base64 encoding of the 32-byte SHA-256 digest (always 44 characters with `=` padding).

### Python Implementation

```python
import hashlib, base64

def compute_authtoken(cert_fingerprint, pairingcode, controllernonce, stbnonce):
    # Stage 1
    stage1_input = bytes.fromhex(cert_fingerprint) + \
                   pairingcode.encode("utf-8") + \
                   controllernonce.encode("utf-8")
    inner = hashlib.sha256(stage1_input).digest()
    
    # Stage 2
    stage2_input = stbnonce.encode("utf-8") + inner + b"biT43y"
    final = hashlib.sha256(stage2_input).digest()
    
    return base64.b64encode(final).decode("utf-8")
```

## 7. Binding

Binding authenticates the client to the STB using the computed auth token. A successful bind grants a `bind_id` that authorises subsequent key commands.

### Bind Request (Client → STB)

```json
{
    "command_name": "Bind Request",
    "tid": "<same-tid-as-pair>",
    "authtoken": "jlp2oeeZCckxptPhKyEheCFBuoRVF+QtDsiIqvE9VKk="
}
```

### Bind Response (STB → Client)

**Success:**
```json
{
    "command_name": "Bind Request",
    "status": true,
    "bind_id": 3,
    "tid": "<echoed-tid>"
}
```

**Failure:**
```json
{
    "command_name": "Bind Request",
    "status": false,
    "tid": "<echoed-tid>"
}
```

| Field | Description |
|-------|-------------|
| `bind_id` | Integer session identifier. Include this in all subsequent key commands. |
| `status` | `true` if authentication succeeded. |

> **Warning:** The STB may lock out after repeated failed bind attempts. If this happens, reboot the STB to clear the lockout. Failed pair-only attempts (without bind) do NOT trigger lockout.

## 8. Sending Commands

After a successful bind, the client can send key commands. The STB responds with `status: true` for recognised keys.

### Key Command Request (Client → STB)

```json
{
    "command_name": "Key Command Request",
    "tid": "<same-tid>",
    "authtoken": "<same-authtoken>",
    "bind_id": 3,
    "cmd": "keyatomic",
    "key": "Enter"
}
```

| Field | Description |
|-------|-------------|
| `command_name` | Must be `"Key Command Request"`. |
| `tid` | Same transaction ID used throughout the session. |
| `authtoken` | Same auth token from the bind step. |
| `bind_id` | The `bind_id` received in the Bind Response. |
| `cmd` | Command type — always `"keyatomic"` for key presses. |
| `key` | The key name (see [§9](#9-key-names-reference)). |

### Key Command Response (STB → Client)

```json
{
    "command_name": "Key Command Request",
    "status": true,
    "tid": "<echoed-tid>"
}
```

If `status` is `false` or the response contains `"error": "unrecognized"`, the key name is not supported by the device.

## 10. Complete Session Example

```
Client                                          STB (192.168.69.149:8091)
  │                                                │
  │──── mDNS Query (_rics._tcp.local.) ──────────>│
  │<─── mDNS Response (IP, port 8091, MAC) ───────│
  │                                                │
  │──── TCP Connect ──────────────────────────────>│
  │──── TLS 1.3 ClientHello (SNI=sky.xcal.tv) ───>│
  │     + Client Certificate (EC P-256)            │
  │<─── TLS 1.3 ServerHello + Finished ───────────│
  │                                                │
  │──── WebSocket Upgrade GET /iptarget ──────────>│
  │<─── 101 Switching Protocols ──────────────────│
  │                                                │
  │──── Pair Request {controllernonce: UUID} ─────>│
  │<─── Pair Response {pairingcode, stbnonce} ────│
  │                                                │
  │  [Client computes authtoken]                   │
  │  cert_fp = SHA256(client_cert_DER)             │
  │  inner = SHA256(cert_fp_bytes ‖ pairingcode    │
  │                 ‖ controllernonce)              │
  │  token = B64(SHA256(stbnonce ‖ inner ‖ biT43y))│
  │                                                │
  │──── Bind Request {authtoken} ─────────────────>│
  │<─── Bind Response {status:true, bind_id:3} ───│
  │                                                │
  │──── Key Command {key:"ArrowDown"} ────────────>│
  │<─── {status: true} ──────────────────────────│
  │──── Key Command {key:"Enter"} ────────────────>│
  │<─── {status: true} ──────────────────────────│
  │                                                │
  │──── WebSocket Close ──────────────────────────>│
```

## 12. Implementation Notes

### What Works
- Full pair → bind → command cycle confirmed working
- 39 verified key names (24 from app enum + 15 box extras); see Section 9
- Multiple sessions can coexist (each gets a unique `bind_id`)
- The `tid` can be reused across all messages in a session

### Gotchas
- **Key names are NOT the W3C standard names.** For example, `VolumeUp` not `AudioVolumeUp`; `AccessMenu` not `Menu`; `Enter` not `Select`; `Backspace` not `Back`.
- **The `command_name` for key commands is `"Key Command Request"`**, not `"keyatomic"`. The `"keyatomic"` value goes in the `"cmd"` field.
- **Manufacturer must be `"Comcast"`** and model must be `"IPRemote"` — other values may be rejected.
- **Failed binds can cause lockout** — the STB may reject all bind attempts until rebooted.
- **The `authtoken` must be included in every key command**, not just the bind.

### Dependencies (Python)
- `websockets` (≥13.0) — WebSocket client
- `zeroconf` — mDNS device discovery
- Python 3.9+ with `ssl`, `hashlib`, `base64` (stdlib)

### Reference Implementation
See `tools/sky_remote.py` for a complete, working Python client with TUI remote control interface.
